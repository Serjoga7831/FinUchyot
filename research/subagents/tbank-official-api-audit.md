## Вывод

Для **обычного физлица с дебетовыми/кредитными картами и счетами Т‑Банка** я не нашёл официального публичного self-service API, через который можно выдать своему приложению токен и программно получать историю карточных покупок/банковских операций. Публично документированный `T‑API` для выписок — это **API Т‑Бизнеса**, а не розничного банка. Наиболее технически и юридически устойчивый путь для личного финансового учёта сейчас — **импорт выписки, сформированной в официальном приложении/интернет-банке**, либо ожидание/подключение к официальной Open Banking-интеграции, когда Т‑Банк откроет для неё внешний контур и условия подключения.

## Чёткое разграничение

| Контур | Можно ли получать операции физлица по обычным картам/счетам? | Что реально даёт |
|---|---:|---|
| **T‑API / API для Т‑Бизнеса** | **Нет**, если речь о личных розничных счетах | Выписки и операции по счетам ООО/ИП в Т‑Бизнесе; прямое подключение требует быть ООО или ИП и иметь доступ к кабинету Т‑Бизнеса. |
| **Партнёрская интеграция T‑API** | Не является публичным API личных операций | Предназначена для владельцев онлайн-сервисов; в документации описаны T‑ID и T‑Business ID. Для финансовых данных клиентов необходим отдельный согласованный партнёрский сценарий, а не токен физлица «по кнопке». |
| **T‑Invest API** | **Да, но только для брокерских/инвестиционных операций** | Портфель, доходность, операции брокерского счёта, заявки, рыночные данные. Это не API истории трат по банковской карте. |
| **Open Banking / Открытые API** | Потенциально да, но публичного массового developer-onboarding Т‑Банка для стороннего PFM-приложения я не обнаружил | Т‑Банк со Сбером запускал пилот с согласиями клиентов; Банк России утвердил стандарты и поэтапное обязательное внедрение. |
| **Вебхуки T‑API** | **Нет для розничного физлица** | Вебхук «Операция по счёту» относится к T‑API/Т‑Бизнесу и подключается по ИНН компании. |
| **Выписка из приложения/интернет-банка** | **Да, вручную** | Законный и устойчивый источник данных для импорта в PFM; автоматизацию загрузки следует делать только вокруг явно поддерживаемого пользователем экспорта, без эмуляции входа. |

## 1) T‑API: это бизнес-API, не API личных покупок

Официальная документация прямо называет T‑API интерфейсом для автоматизации бизнес-процессов и указывает: **«Только для юридических лиц»**. Для старта требуются регистрация как **ООО или ИП** и доступ в личный кабинет Т‑Бизнеса.[1]

У T‑API есть метод выписки:

- `GET https://business.tbank.ru/openapi/api/v1/statement`;
- возвращает операции по счёту за период, включая, среди прочего, сумму, описание, MCC, данные торговой точки и статус операции;
- авторизация — Bearer API Token;
- лимит — **20 запросов/сек**;
- постраничная выдача: до 5 000 операций за запрос, `nextCursor`;
- данные по этому API доступны с июня 2023 года.[2]

Но сам endpoint расположен в контуре `business.tbank.ru`, а требуемый scope сформулирован как информация об операциях **компании** с ИНН/КПП. Это не основание использовать его для личной дебетовой карты физлица.[2]

**Вывод:** не следует пытаться «переиспользовать» T‑API для личного учёта, если пользователь не ведёт учёт операций своего ИП/ООО.

## 2) Партнёрский API: не равен доступу к транзакциям физлица

Т‑Банк описывает партнёрскую интеграцию как сценарий для владельца онлайн-сервиса, которому нужен доступ к данным клиентов Т‑Банка. В открытой документации перечислены два механизма:

- **T‑ID** — авторизация пользователей Т‑Банка;
- **T‑Business ID** — авторизация клиентов со счетом в Т‑Бизнесе.[3]

То есть T‑ID можно использовать для идентификации и авторизации пользователя в стороннем сервисе, но из опубликованной документации **не следует**, что T‑ID сам по себе выдаёт доступ к истории его покупок или к банковской выписке.

Для продукта личного финансового учёта это означает: можно обсуждать с Т‑Банком индивидуальную партнёрскую/Open Banking-интеграцию, но нельзя проектировать систему с допущением, что любой пользователь сможет сам выпустить универсальный consumer API-token к операциям по картам.

## 3) Вебхуки: только в бизнес-контуре

Вебхук **«Операция по счёту»** запускается при появлении новой операции или изменении прежней; банк отдельно предупреждает, что события могут дублироваться, поэтому нужна идемпотентность по `OperationId`.[4]

Однако подключение T‑API-вебхуков требует:

- HTTPS, порт 443, POST;
- обращения на `openapi@tbank.ru` или через чат Т‑Бизнеса;
- указания **ИНН компании**;
- до двух рабочих дней на подключение;
- при ошибке доставки — до пяти повторов с интервалами от 30 секунд до 10 минут.[5]

Следовательно, это хорошая модель для **ИП/ООО**, но не официальный webhook-механизм для личной банковской карты физлица.

## 4) T‑Invest API: официальный путь именно для инвестиций

Для клиента Т‑Инвестиций есть отдельный публичный **T‑Invest API** — gRPC-интерфейс к торговой платформе. Он позволяет получать портфель, доходность, операции брокерского счёта, рыночные данные и работать с заявками.[6]

Для истории инвестиционных операций подходит `GetOperationsByCursor`: он поддерживает пагинацию и фильтры; лимит ответа по умолчанию 100, максимум 1 000 операций.[7]

Доступ осуществляется официально выпущенным токеном. Для PFM следует использовать **Read-only token** либо токен с доступом к конкретному счёту и правом read-only — он даёт данные портфеля/операций, но не позволяет выставлять заявки. Срок жизни токена — три месяца с последнего использования; его можно отозвать в настройках безопасности.[8]

Ограничение принципиально: T‑Invest API охватывает **брокерский контур**, а не обычные платежи по дебетовой/кредитной карте.

## 5) Open Banking: перспективный, но пока не доказанно открытый self-service путь

Т‑Банк и Сбер в октябре 2024 года сообщали о тестировании Open Banking на группе клиентов: пользователи могли после отдельного согласия видеть балансы, а заявленная модель включала историю операций и управление согласиями. В той публикации прямо сказано, что это был пилот/бета, а не публичный API-каталог для всех сторонних разработчиков.[9]

Со стороны регулирования направление развивается:

- Банк России указывает, что Open API предназначены в том числе для сервисов планирования личных финансов, объединяющих данные физлица из разных организаций.[10]
- На странице регулятора опубликованы спецификации от 19 декабря 2025 года для **получения согласия** и **получения информации о банковских счетах физических лиц**.[11]
- Банк России анонсировал поэтапную обязательность Open API с 2026 года для крупнейших банков, брокеров и страховщиков.[10]

**Практическая оценка:** стандарты и пилоты есть, но в доступных официальных материалах Т‑Банка я не нашёл опубликованных внешних endpoint’ов, публичной регистрации независимого PFM-провайдера, sandbox и условий production-доступа именно к счетам физлиц. Поэтому Open Banking стоит рассматривать как целевую архитектуру, но не как гарантированно доступную интеграцию «прямо сейчас».

## Рекомендованная архитектура для PFM

1. **Банковские траты физлица:** импорт выписки, которую пользователь сам сформировал и выгрузил в официальном Т‑Банке; хранить только минимально нужные нормализованные данные.
2. **Инвестиции:** официальный T‑Invest API с отдельным read-only токеном, по возможности с ограничением конкретным брокерским счётом.
3. **Будущее подключение счетов:** заложить модуль `open_banking_connector`, который работает через явное согласие пользователя, OAuth/OpenID Connect-подобный авторизационный поток и отзыв согласия/доступа.
4. **Не делать:** screen scraping, автоматизацию входа в личный кабинет, обход 2FA, извлечение сессионных токенов, хранение пароля пользователя.
5. **Для переговоров с банком:** запросить у `openapi@tbank.ru` именно статус production-доступа для партнёрского PFM-сценария: доступные данные, модель согласий, требования к организации/инфобезопасности, sandbox, аудит, тарифы и SLA.
