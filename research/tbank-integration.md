# Подключение Т‑Банка к FinUchyot

**Дата исследования:** 13 августа 2026 года  
**Задача:** получать сведения о собственных покупках и иных операциях физического лица.

## Краткий вывод

Подключение технически возможно четырьмя способами, но они сильно различаются по устойчивости и риску:

1. **Официальный Open Banking** — лучший стратегический вариант, однако публичного self-service API Т‑Банка, куда обычное приложение физлица может получить клиентский токен и читать личные карточные операции, не обнаружено. Действующий T‑API на портале разработчика предназначен для юридических лиц и бизнес-счетов. Российский стандарт Open API для информации о счетах физлиц уже опубликован, а Т‑Банк применяет его в своем мультибанкинге с банками-партнерами, но доступ для произвольного независимого приложения требует отдельного партнерского/регуляторного подключения.
2. **Экспорт операций из личного кабинета** — самый безопасный и надежный способ для MVP и исторической загрузки. Т‑Банк официально разрешает выбрать период и продукты, затем выгрузить все операции через личный кабинет на компьютере.
3. **Android Notification Listener** — практически удобный способ получать новые покупки почти сразу после уведомления. Он не дает полную историю и требует последующей сверки с банковской выгрузкой.
4. **Отдельная сессия приватного web API Т‑Банка** — технически возможна и существует в открытых сторонних клиентах, включая получение счетов, операций и электронных чеков. Но это не официальный публичный контракт: он может измениться без предупреждения, потребует работы с банковской сессией и может противоречить условиям обслуживания. Для основной версии FinUchyot этот вариант не рекомендуется.

## 1. Официальные API

### T‑API для бизнеса

Официальный портал T‑API содержит методы счетов и выписок, токены, mTLS и песочницу. При этом руководство по началу работы прямо помечено **«Только для юридических лиц»**. Выпуск защищенного доступа связан с кабинетом бизнеса, фиксированным IP и mTLS-сертификатом. Это не API личной дебетовой карты физлица.[1][2]

T‑Invest API также не решает задачу: он предназначен для брокерских счетов и инвестиционных операций, а не покупок по банковским картам.

### Open Banking для физлиц

Банк России опубликовал стандарты:

- получения согласия на доступ к банковским счетам физлица;
- получения информации о счетах физлица;
- OIDC/FAPI-профили безопасности.[3]

Т‑Банк уже использует эту технологию. В 2024 году он сообщил о тесте со Сбером: после явного согласия клиента приложения банков показывают балансы и историю операций другого банка. В 2025 году Т‑Банк объявил мультибанкинг со Сбером, ВТБ и Альфа‑Банком.[4][5]

Это доказывает техническую доступность банковского Open Banking, но **не означает наличия открытой регистрации для любого приложения**. В публичных материалах не найдено:

- developer console для регистрации независимого приложения физлица;
- OAuth/OIDC client ID, который может получить обычный разработчик без партнерского договора;
- публичный production endpoint личных карточных операций;
- тариф и процедура подключения независимого поставщика информации о счетах.

### Что делать для официального подключения

Для продуктовой версии необходимо обратиться в Т‑Банк как потенциальный партнер и запросить:

1. доступ к API информации о счетах физлиц по стандартам Банка России;
2. требования к юридическому лицу и статусу участника;
3. sandbox, dynamic client registration либо выдачу client ID;
4. требования к FAPI/OIDC, mTLS, российской криптографии и журналированию согласий;
5. scope только на чтение счетов, балансов и операций;
6. правила отзыва и срока действия согласия;
7. возможность получать webhooks либо incremental cursor.

Для личного локального проекта это, вероятнее всего, непропорционально сложно. Для коммерческого агрегатора — правильный путь.

## 2. Официальный экспорт операций

Т‑Банк документирует экспорт всех операций:

1. войти в личный кабинет на компьютере;
2. открыть вкладку **«Операции»**;
3. выбрать период и нужные продукты;
4. нажать «Поделиться» и выбрать формат выгрузки.[6]

Также доступны:

- справка с движением средств за выбранный период;
- PDF-выписка за расчетный период;
- справка и, при наличии, электронный чек по конкретной операции.[6][7]

### Рекомендуемая реализация в FinUchyot

Сделать локальный импортёр с интерфейсом `BankStatementImporter`:

```text
файл пользователя
  → определение формата/кодировки
  → разбор строк
  → нормализация суммы, валюты, даты и статуса
  → сопоставление счета
  → дедупликация
  → предварительный просмотр
  → подтверждение импорта
```

Поля нормализованной операции:

- внешний идентификатор, если присутствует;
- счет/карта и последние четыре цифры;
- время авторизации и время окончательного списания;
- сумма операции и сумма в валюте счета;
- валюта;
- статус (`pending`, `posted`, `reversed`);
- описание/merchant;
- MCC и банковская категория, если присутствуют;
- кэшбэк;
- комментарий;
- hash исходной строки для повторной дедупликации.

Импорт должен быть идемпотентным: повторная загрузка того же файла не создает дубли. Нельзя считать совпадение только по дате и сумме — две одинаковые покупки в один день возможны.

**Плюсы:** официальный путь, полная история, минимальный риск блокировки, не нужны пароль и банковская сессия.  
**Минусы:** ручное действие; возможна задержка; набор колонок зависит от формата выгрузки.

## 3. Получение покупок из Android-уведомлений

Т‑Банк сообщает, что при подключенной услуге оповещений отправляет push-уведомления обо всех операциях, снятиях и пополнениях; если push не доставлен, может отправить SMS.[8]

Android предоставляет `NotificationListenerService`, которому пользователь отдельно выдает доступ к уведомлениям.[9]

### Архитектура

```text
уведомление пакета Т‑Банка
  → фильтр по package name
  → локальный parser шаблонов
  → PendingTransaction
  → сопоставление с банковским счетом
  → уведомление пользователю о новой записи
  → поздняя сверка с экспортом/официальным API
```

Требования безопасности:

- обрабатывать только пакет Т‑Банка, а не сохранять все уведомления телефона;
- никогда не сохранять OTP, коды входа, сообщения чата и посторонние уведомления;
- не отправлять исходный текст на внешний сервер;
- хранить только разобранные поля операции;
- шифровать локальную базу;
- дать пользователю журнал того, что было импортировано;
- использовать явное согласие и отдельный выключатель интеграции.

**Плюсы:** почти real-time, не нужен пароль банка, устойчивее приватного API.  
**Минусы:** только новые события; пропущенное уведомление не восстановить; текст push может меняться или скрывать данные; авторизация покупки позже может быть отменена или проведена на другую сумму; Android/прошивка может ограничивать фоновую работу. Поэтому записи сначала должны иметь статус `pending`, а экспорт — подтверждать их.

SMS-парсер может быть резервным каналом, но разрешение на чтение SMS еще чувствительнее и ограничивает публикацию приложения в магазине. Для локальной установки возможно сделать отдельный необязательный модуль, но основным каналом его выбирать не стоит.

## 4. Отдельная банковская сессия и приватный API

### Что найдено

Открытый MIT-проект `jfk9w-go/tbank-api` описывает клиент приватного web API Т‑Банка. Он умеет:

- проводить авторизацию через web flow;
- сохранять и повторно использовать сессию;
- получать счета;
- получать операции;
- получать доступные электронные кассовые чеки.[10]

В текущем коде авторизация запускает управляемый браузер, проходит банковский login flow и извлекает cookie сессии `psid`. Далее запросы используют приватные методы, в частности `/common/v1/operations`; структура операции содержит сумму, валюту, merchant, MCC, категорию, кэшбэк, координаты и признак электронного чека. Это подтверждает, что технически такой коннектор возможен.

Архивный плагин ZenMoney для Тинькофф 2016 года работал сходным образом: принимал логин и пароль, привязывал устройство по SMS, создавал `sessionid`, вызывал `accounts_flat` и `operations`, а затем импортировал счета и операции.[11] Этот код десятилетней давности нельзя считать описанием современной синхронизации ZenMoney.

### Почему не стоит брать это как основной способ

- API не документирован банком как публичный контракт;
- endpoint, поля, anti-bot и процесс входа могут измениться в любой день;
- новая авторизация может требовать CAPTCHA, MFA или подтверждения устройства;
- утечка session cookie эквивалентна компрометации банковской сессии;
- серверный запуск потребует хранить высокочувствительный секрет;
- банк может завершать сессии или ограничивать подозрительную автоматизацию;
- отсутствуют официальные гарантии scope «только чтение»;
- возможны ограничения условий дистанционного банковского обслуживания.

### Если использовать только как локальный эксперимент

Допустима исследовательская реализация при следующих ограничениях:

- только локально на устройстве пользователя;
- интерактивный вход на официальной странице Т‑Банка;
- приложение не получает и не сохраняет пароль;
- session cookie хранится в Android Keystore/аппаратно защищенном хранилище;
- cookie никогда не передается на сервер FinUchyot и не попадает в логи/резервные копии;
- доступ только на чтение; методы платежей и переводов не реализуются;
- при любой MFA пользователь подтверждает действие сам;
- есть кнопка «Удалить сессию» и понятная индикация срока действия;
- перед использованием запрашивается письменное разрешение/позиция банка.

Даже при этих мерах это остается **экспериментальным неофициальным коннектором**, а не надежной производственной интеграцией.

## 5. Рекомендуемая дорожная карта

### Этап A — безопасный MVP

1. Реализовать модель счетов и операций.
2. Добавить ручной импорт официальной выгрузки Т‑Банка.
3. Собрать несколько обезличенных образцов разных доступных форматов.
4. Реализовать preview, mapping колонок, дедупликацию и повторный импорт.
5. Не хранить банковские учетные данные.

### Этап B — оперативные покупки на Android

1. Добавить локальный Notification Listener.
2. Поддержать только пакет приложения Т‑Банка.
3. Создавать предварительные (`pending`) покупки.
4. Разрешить пользователю исправлять merchant/категорию.
5. Сверять и подтверждать их при следующем импорте выписки.

### Этап C — официальный канал

1. Обратиться в Т‑Банк с описанием FinUchyot.
2. Запросить партнерский Open Banking read-only доступ.
3. После получения документации реализовать OIDC/FAPI consent flow.
4. Никогда не запрашивать банковский пароль внутри FinUchyot.

### Этап D — эксперимент с отдельной сессией

Рассматривать только после письменного ответа Т‑Банка и отдельно от основной ветки продукта. Не включать в публичную сборку по умолчанию.

## Итоговое решение

Для FinUchyot оптимальна **гибридная схема**:

```text
Notification Listener → быстрые предварительные покупки
Экспорт Т‑Банка       → полная история и сверка
Open Banking          → будущая официальная автоматизация
```

Она дает полезную автоматизацию уже сейчас, не требует передавать банковский пароль и не делает проект зависимым от закрытого API. Приватная сессия технически реализуема, но должна оставаться необязательным исследовательским прототипом.
