# HANDOFF — безопасный эксперимент с браузерной сессией Т‑Банка

**Проект:** FinUchyot  
**Репозиторий:** https://github.com/Serjoga7831/FinUchyot  
**Дата передачи:** 13 августа 2026 года  
**Статус:** исследование завершено; реализация браузерного прототипа ещё не начиналась.

## 1. Цель следующего агента

Проверить минимально рискованный вариант получения официальной выгрузки собственных операций Т‑Банка через **реальный Chromium с отдельным постоянным профилем**:

```text
интерактивный вход пользователя на tbank.ru
  → сохранение браузерной сессии в изолированном локальном профиле
  → повторное открытие кабинета без автоматизации аутентификации
  → переход к официальному разделу операций
  → формирование и скачивание штатного экспорта
  → локальный импорт файла в FinUchyot
```

Эксперимент должен подтвердить или опровергнуть:

1. сохраняется ли авторизованная банковская сессия между перезапусками отдельного профиля;
2. можно ли повторно открыть раздел операций без нового SMS/PUSH-кода;
3. доступен ли штатный экспорт операций и какие форматы он предлагает;
4. можно ли автоматизировать **только навигацию и скачивание экспорта**, не обращаясь напрямую к приватному API;
5. как корректно обнаруживать истечение сессии и возвращать управление пользователю.

## 2. Жёсткие ограничения

### Запрещено

- Рассматривать, анализировать, копировать или использовать исходный код ZenMoney.
- Эмулировать мобильное приложение Т‑Банка.
- Воспроизводить закрытый протокол аутентификации запросами HTTP.
- Перехватывать SMS, PUSH, OTP или PIN/код быстрого входа.
- Просить пользователя передавать номер телефона, код, пароль или банковские данные в чат.
- Читать, экспортировать, печатать или журналировать cookies, localStorage, IndexedDB, заголовки авторизации и другие сессионные секреты.
- Использовать stealth/anti-detect, подмену fingerprint, обход CAPTCHA, MFA, device binding или антибот-защиты.
- Вызывать приватные JSON/API endpoint Т‑Банка напрямую.
- Автоматизировать переводы, платежи, изменение профиля, реквизитов или настроек безопасности.
- Запускать банковский профиль на VPS, в контейнере общего назначения или в облачном браузере.
- Коммитить браузерный профиль, банковские файлы, логи с финансовыми данными или скриншоты кабинета в Git/GitHub.
- Подключать к профилю синхронизацию Google/Chromium или расширения.

### Обязательно

- Вход выполняет сам пользователь только на официальном домене Т‑Банка.
- При появлении формы входа, CAPTCHA, MFA, OTP, подтверждения нового устройства или неожиданного разрешения автоматизация немедленно останавливается.
- Прототип должен работать fail-closed: неизвестная страница или изменившаяся разметка не приводит к случайным кликам.
- Банковский профиль хранится вне репозитория и исключён из резервных копий/синхронизации.
- В журнале допускаются только технические события без URL query, HTML, текстов операций и персональных данных.
- Должна быть команда полного удаления локального банковского профиля.
- Пользователю нужно напомнить отозвать соответствующую сессию в приложении Т‑Банка после окончания эксперимента.

## 3. Важный контекст и установленные факты

- Публичного self-service API для операций по личным картам Т‑Банка не найдено.
- Официальный T‑API счетов и выписок относится к Т‑Бизнесу; T‑Invest API — к инвестициям.
- Т‑Банк официально позволяет экспортировать все операции из личного кабинета на компьютере: раздел «Операции» → период/продукты → «Поделиться» → формат файла.
- Пользователь лично наблюдал, что современное подключение Т‑Банка в ZenMoney после номера телефона и одноразового кода создаёт отдельную активную банковскую сессию.
- Публичные материалы ZenMoney описывают локальную синхронизацию с телефона, однако точный современный транспорт не раскрыт. Исходный код ZenMoney использовать запрещено.
- Для FinUchyot предлагается независимый браузерный эксперимент, основанный только на официальном веб-интерфейсе Т‑Банка.

## 4. Предпочтительная архитектура прототипа

Не использовать WebView на первом этапе. Предпочтителен полноценный локальный Chromium/Chrome с отдельным `user-data-dir`.

```text
apps/tbank-browser-connector/
├── README.md
├── config.example.*
├── src/
│   ├── profile/          # создание/удаление изолированного профиля
│   ├── browser/          # запуск реального Chromium
│   ├── state/            # logged_out / user_action / ready / exporting
│   ├── export/           # только штатная UI-навигация и download
│   └── audit/            # обезличенный журнал событий
└── tests/
    ├── fixtures/         # только искусственные страницы/данные
    └── ...
```

Каталог реального профиля должен находиться, например, в пользовательском data directory вне Git:

```text
~/.local/share/finuchyot/bank-profiles/tbank/
```

Но перед созданием каталога проверить, что текущая машина действительно является доверенным локальным устройством пользователя, а не VPS. На VPS эксперимент не проводить.

## 5. Предлагаемый стек

Допустимы Playwright или Selenium только как контроллер настоящего установленного Chromium. Требования:

- `headless=false` для первичного входа и всех повторных подтверждений;
- persistent context / отдельный user data directory;
- без stealth-плагинов;
- без чтения cookie storage программой;
- без перехвата response body банковских API;
- download через штатное действие интерфейса;
- строгий allowlist origin: только подтверждённые официальные HTTPS-домены Т‑Банка;
- автоматическое прекращение работы при переходе на неизвестный origin.

Если браузер или сайт не допускает безопасную автоматизацию интерфейса, зафиксировать ограничение и остановиться — не переходить к обходным методам.

## 6. Этапы работы и точки согласования

### Этап 0 — только безопасный dry-run

До взаимодействия с реальным банком:

1. Определить, локальная ли машина и допустимо ли хранить на ней банковскую сессию.
2. Проверить установленный Chromium/Chrome и доступные средства автоматизации.
3. Создать каркас коннектора.
4. Создать искусственную тестовую страницу, имитирующую состояния `logged_out`, `ready`, `export_available`.
5. Проверить lifecycle отдельного профиля и удаление данных.
6. Проверить, что журналы не содержат содержимого страниц и секретов.
7. Добавить `.gitignore` для profiles, downloads, traces, screenshots, HAR и временных банковских файлов.
8. Запустить тесты на искусственных данных.

### Стоп перед реальным входом

Перед открытием реального кабинета агент обязан показать пользователю:

- точную схему действий;
- какие файлы будут созданы и где;
- какие процессы будут запущены;
- риски компрометации сессии;
- способ остановки и полного удаления;
- план отзыва сессии в Т‑Банке;
- подтверждение, что OTP/PIN не будут перехватываться.

Реальный вход допускается только после отдельного явного согласия пользователя.

### Этап 1 — ручная авторизация

После согласия:

1. Запустить видимый Chromium с отдельным профилем.
2. Открыть официальный URL личного кабинета.
3. Передать управление пользователю.
4. Не снимать скриншоты и не записывать trace/HAR/video.
5. Дождаться, пока пользователь сообщит, что вход завершён.
6. Закрыть браузер штатно.
7. Повторно запустить тот же профиль и проверить только факт сохранения входа.

Не просить пользователя сообщать агенту номер, OTP или код быстрого входа.

### Этап 2 — экспорт

1. В видимом режиме перейти к официальному разделу операций.
2. Определить доступные элементы экспорта без выполнения финансовых действий.
3. Перед скачиванием показать пользователю, что будет выбрано: период, счета, формат, destination.
4. Скачать один тестовый экспорт в защищённый временный каталог.
5. Не коммитить и не отправлять файл.
6. Зафиксировать только название формата, размер и успешность скачивания; не содержимое операций.
7. После подтверждения импорта удалить исходный файл либо переместить в согласованное зашифрованное хранилище.

### Этап 3 — импортёр

На первом проходе импортёр проектировать по реальному формату, но:

- для тестов создать полностью синтетическую обезличенную фикстуру;
- не добавлять реальную выписку в fixtures;
- обеспечить preview и подтверждение;
- обеспечить идемпотентность;
- учитывать pending/posted/reversed, возвраты и одинаковые покупки;
- не логировать строки исходного файла.

## 7. Критерии успешного эксперимента

Минимальный успех:

- отдельный профиль создаётся вне Git;
- пользователь проходит официальный вход самостоятельно;
- сессия сохраняется между двумя перезапусками браузера;
- повторный запуск корректно определяет `ready` либо `user_action_required`;
- штатный экспорт можно скачать через UI;
- ни один секрет или банковский файл не попал в Git/логи;
- профиль можно полностью удалить;
- тесты на синтетической странице проходят.

Эксперимент считается неудачным, но корректно завершённым, если:

- банк блокирует отдельный профиль/автоматизацию;
- каждое открытие требует MFA;
- UI невозможно надёжно распознать без рискованных кликов;
- нет штатного экспорта нужной полноты;
- политика безопасности браузера не позволяет безопасно сохранить сессию.

В этих случаях агент должен остановиться и предложить ручной импорт, а не обход защиты.

## 8. Модель состояний

```text
UNINITIALIZED
  → PROFILE_READY
  → LOGIN_REQUIRED
  → USER_AUTHENTICATING
  → SESSION_READY
  → EXPORT_REVIEW
  → EXPORTING
  → FILE_READY
  → IMPORT_PREVIEW
  → COMPLETED

Любое неожиданное состояние
  → STOPPED_USER_ACTION_REQUIRED
```

Запрещены автоматические переходы через `LOGIN_REQUIRED` и `USER_AUTHENTICATING`.

## 9. Безопасное логирование

Разрешённый пример:

```json
{"event":"browser_started","profile":"tbank","mode":"visible"}
{"event":"state_changed","from":"LOGIN_REQUIRED","to":"USER_AUTHENTICATING"}
{"event":"session_check","result":"ready"}
{"event":"export_download","format":"unknown","result":"success"}
```

Запрещено логировать:

- телефон;
- ФИО;
- номера счетов и карт;
- баланс и суммы;
- merchant;
- OTP/PIN;
- cookies/tokens;
- полный URL с query/fragment;
- DOM/HTML;
- имя реального банковского файла.

## 10. Откат и завершение эксперимента

1. Остановить процесс браузерного коннектора.
2. Удалить временные downloads.
3. Удалить каталог отдельного browser profile безопасной командой приложения.
4. Завершить соответствующую активную сессию в официальном приложении Т‑Банка.
5. Проверить `git status` и убедиться, что никаких profile/download/log artifacts нет.
6. Если были созданы зависимости или системные службы, удалить их и документировать откат.

## 11. Требования к коммитам и публикации

- Не коммитить ничего, связанного с реальной банковской сессией.
- Перед каждым коммитом запускать secret scan, `git diff --check` и тесты.
- Реализацию вести в отдельной feature-ветке.
- Не сливать в `main` без проверки пользователя.
- В PR описать угрозы, ограничения, сценарий удаления профиля и результаты dry-run.
- Не заявлять, что интеграция официально поддерживается Т‑Банком.

## 12. Первый конкретный шаг следующего агента

Сначала выполнить только read-only диагностику окружения и подготовить план dry-run. Не устанавливать браузеры, драйверы или библиотеки и не создавать реальный банковский профиль до согласования с пользователем.

После диагностики выдать:

1. выбранный локальный runtime;
2. расположение будущего профиля;
3. перечень файлов проекта;
4. модель угроз;
5. команды тестирования и удаления;
6. план изменений с рисками и откатом.

Только после одобрения переходить к реализации dry-run.
